# Secrets with Phase

Central documentation for secret management via [Phase](https://phase.dev), used by both sibling modules:

- `secrets_read` (this module): reads secrets that are **provided** manually (data source `phase_secrets`)
- [`secrets_write`](../secrets_write): writes secrets that are **managed** (generated) by OpenTofu (resource `phase_secret`)

## Concept: environments and paths

Phase app `angkor` has three environments, each with two folders (paths):

| Path | Maintained by | Used by |
|---|---|---|
| `/provided` | manually in the [Phase console](https://console.phase.dev), never touched by tf | read via `secrets_read` (default `path`) |
| `/managed` | OpenTofu via `secrets_write` (default `path`), key = uppercased `name`, comment "created by tofu" | consumers (EC2, GitHub Actions) |

| Environment | Module instances in `../../main.tf` | Consumer |
|---|---|---|
| `development` | `secrets_write_dev` | local development |
| `staging` | `secrets_read_ci`, `secrets_write_ci` | **GitHub Actions**: Phase syncs **only `staging` → `/managed`** to the repository's Actions secrets |
| `production` | `secrets_read` (should be renamed `secrets_read_prod`), `secrets_write_prod` | **EC2**: `files/appctl.sh` pulls **all** secrets of the env (no path, so `/managed` *and* `/provided`) into the `.env` used by docker compose |

A manually provided secret that a consumer needs from the *other* folder must be copied over by tf. Example: `SONAR_TOKEN` is maintained in `staging` → `/provided`, but GitHub only receives `/managed`, so `secrets_write_ci` copies it:

```hcl
module "secrets_write_ci" {
  # ...
  secrets = [
    # SONAR_TOKEN is maintained manually in /provided, but only /managed is synced to GitHub Actions secrets
    {
      name  = "sonar_token"
      value = module.secrets_read_ci.secrets["SONAR_TOKEN"]
    },
  ]
}
```

### Secrets provided manually (`/provided`)

| Env | Key | Used for |
|---|---|---|
| `staging` | `SONAR_TOKEN` | SonarCloud analysis in CI (copied to `/managed`), `make sonar` via `~/.angkor/.env` |
| `production` | `GRAFANA_SA_TOKEN`, `GRAFANA_CLOUD_ACCESS_POLICY_TOKEN` | grafana module / provider |
| `production` | `NEON_API_KEY`, `NEON_PROJECT_ID` | neon provider / database module |
| `production` | `APPCTL_REPLICA_DB_URL` | `.env_config` (db replica for `appctl.sh`) |

Everything else (Kafka API keys, DB credentials, OAuth2 client secret, release name/version, ...) is generated by tf and written to `/managed`, see the `secrets_write_*` blocks in `../../main.tf`.

## Bootstrapping: who can access Phase?

| Who | Credential | Where it comes from |
|---|---|---|
| OpenTofu (phase provider) | `var.phase_cli_token` (`pss_service:v2:...`, alternatively env `PHASE_TOKEN`) | `terraform.tfvars`, service account @ <https://console.phase.dev/timafe/access/service-accounts> |
| EC2 (`appctl.sh`) | `PHASE_APP_ID`, `PHASE_API_TOKEN` (REST API token, *without* the `ServiceAccount` prefix) | SSM parameters `/angkor/prod/PHASE_*`, written by tf (`module "param"` in `../../main.tf`) |
| GitHub Actions | none, secrets are pushed by Phase | Phase GitHub Actions sync (see below) |

The phase provider is not on registry.opentofu.org, so it's declared as `registry.terraform.io/phasehq/phase`.

## Updating a provided secret (e.g. renew `SONAR_TOKEN`)

1. Create the new value (e.g. SonarCloud → My account → Access tokens, choose a long expiry and set a reminder, SonarCloud deletes expired tokens).
2. Set it in the Phase console: app `angkor` → `staging` → `/provided` → `SONAR_TOKEN`.
3. Let tf distribute it (`terraform/`), a targeted apply is enough:

   ```bash
   AWS_PROFILE=timafe tofu plan  -target=module.secrets_write_ci -target=local_file.dotenv -target=aws_s3_object.dotenv
   AWS_PROFILE=timafe tofu apply -target=module.secrets_write_ci -target=local_file.dotenv -target=aws_s3_object.dotenv
   ```

   This writes `staging` → `/managed` → `SONAR_TOKEN` and regenerates `~/.angkor/.env` and the S3 `deploy/.env_config` (`main_objects.tf`). A full `make apply` does the same.
4. Phase syncs `/managed` to GitHub within seconds, check with `gh secret list` (updated timestamp).
5. Re-run failed workflows, e.g. `gh run rerun <run-id> --failed`.

Symptom of an expired token in CI: `ERROR Failed to query JRE metadata: . Please check the property sonar.token or the environment variable SONAR_TOKEN.`

## Phase API: programmatic secret access

> Secrets are key/value pairs used to store application secrets or environment variables for your applications. Secrets in Phase can additionally have tags and comments associated with them (see <https://docs.phase.dev/public-api/secrets>).

```bash
$ curl -fsSLGH "Authorization: Bearer ServiceAccount $(cat ~/.secret/PHASE_API_TOKEN)" \
    "https://api.phase.dev/v1/secrets/" \
    -d app_id="$(cat ~/.secret/PHASE_APP_ID)" \
    -d env="development" \
    -d path="/" | \
    jq -r '.[] | "\(.key)=\(.value)"'

KEY_1=****
KEY_2=*****
(...)
```

> [!NOTE]
> If you omit the `-d path="/xyz"` parameter, all secrets in the env will be returned. If you use `/`, only secrets at the root level will be returned. You can also specify sub-paths like `/managed` to get secrets under that path. Use `-d key=keyname` to get a specific secret.

## Setup Phase GitHub Actions secret sync

Follow the [Phase docs](https://docs.phase.dev/integrations/platforms/github-actions?auth-method-cloud=access-token), use the Personal Access Token (PAT) approach with the following repo specific permissions:

- Actions - Access: Read-only
- Environments - Access: Read and write
- Metadata - Access: Read-only (auto-selected)
- Secrets - Access: Read and write

Then use them in workflows like `-e KAFKA_PRODUCER_API_SECRET="${{secrets.KAFKA_PRODUCER_API_SECRET}}"`.

> [!CAUTION]
> Existing secrets in your repo will be wiped out (!), and you can only sync **one path** within an environment, here `staging` → `/managed`. You can also add secrets manually to that path, they will be left alone by tf (but don't use the same key as a tf managed secret).

## Gotchas

- **Secrets end up in the tf state**: everything read via `secrets_read` or written via `secrets_write` is stored (as sensitive value) in the remote state, so protect the state bucket accordingly.
- **Force re-creation of a managed secret**: delete it in Phase and, if necessary, remove it from the state, e.g.
  `tofu state rm 'module.secrets_write_ci.phase_secret.secret["kafka_producer_api_secret"]'`
- **Keys are uppercased** by `secrets_write` (`upper_key = true` by default), so `name = "sonar_token"` becomes `SONAR_TOKEN`.
- **Don't set tags** on `phase_secret`: they must be pre-created in the Phase console and cause permanent diffs.
- **`-target` warning**: OpenTofu prints a warning that `-target` is meant for exceptional situations, that's expected for the targeted apply above.
- **Changing a value in `/provided` alone does nothing** for GitHub or the local `.env`, a `tofu apply` is required to propagate it (EC2 picks up `production` secrets on the next `appctl.sh` pull).
